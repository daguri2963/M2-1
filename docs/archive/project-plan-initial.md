# 다이소 영양제 선택 지원 AI 서비스 개발 계획서

작성 상태: 기획 초안  
팀 구성: 5인  
개발 기간: 4주 제안 — 실제 마감일에 맞춰 조정  
서비스명: 미정

> 작성 전제: 개발 기간과 기술 스택은 제안이며 팀에서 확정해야 합니다. 다이소몰 상품 상세를 열람하지 못해 실제 제품명·가격·함량 수집은 완료되지 않았습니다. 미검증 상품 정보를 임의로 채우지 않고 초기 수집·검수 작업으로 반영했습니다.

## 1. 프로젝트 개요

영양제를 처음 구매하는 일반 성인이 자신의 관심 건강 분야, 식습관, 현재 섭취 중인 영양제 등을 바탕으로 다이소 영양제를 탐색하고 비교할 수 있는 웹 서비스를 개발한다.

사용자는 설문 또는 AI 대화로 조건을 입력하고, 제품별 성분·함량·가격·표시 섭취방법과 추천 근거를 확인한다. 다이소 제품과 비교할 수 있는 다른 제품도 제공한다.

핵심 가치는 **“영양제를 잘 모르는 사람도 제품 정보를 이해하고, 근거를 확인하며 첫 구매 후보를 좁힐 수 있도록 돕는 것”**이다.

## 2. 문제 정의와 타깃 사용자

주요 타깃은 영양제 구매 경험이 적거나 처음 구매하려는 일반 성인이다. 기존 섭취 제품과 새 제품을 비교하고 싶은 사람도 지원한다.

해결할 문제는 다음과 같다.

- 제품이 많아 어떤 기준으로 선택해야 할지 모른다.
- 성분명과 함량 표시를 이해하기 어렵다.
- 자신의 관심 분야와 제품의 기능성을 연결하기 어렵다.
- 기존 영양제와 성분이 겹치는지 파악하기 어렵다.
- 부담이 적은 제품으로 시작한 뒤 다른 제품과 비교하고 싶다.

설문만으로 영양 결핍이나 질환을 판정하지 않는다. 추천 결과는 입력 조건에 따른 **제품 선택 참고 정보**로 제공한다.

## 3. 서비스 범위와 추천 원칙

| 구분 | 구현 방향 |
|---|---|
| 대상 | 일반 성인의 제품 탐색·선택 지원 |
| 개인 건강 상태 | 추천 제한·주의 안내를 위한 최소 정보로 활용 |
| 섭취량 안내 | 해당 제품의 표시 섭취량·횟수·방법을 출처와 함께 제공 |
| 성분 중복 | 등록된 제품 사이의 중복 성분과 확인 가능한 함량 표시 |
| 대안 제품 | 다이소 제품과 목적·성분이 유사한 다른 제품 비교 |
| 정보 부족 | 추정하지 않고 추가 질문 또는 확인 불가 안내 |

섭취량 안내는 제품 라벨을 기준으로 하며, AI가 개인별 용량을 새로 정하거나 증량하도록 안내하지 않는다. 식약처도 표시된 섭취량·방법·주의사항 확인과 질환·의약품 복용 시 상담을 안내하고 있다. [식약처 섭취 안내](https://impfood.mfds.go.kr/CFBBB02F02/getCntntsDetail?cntntsSn=282629)

‘상위호환 제품 추천’은 **‘비교 가능한 대안 제품 추천’**으로 구현한다. 비교 기준은 1일 섭취량당 성분·함량, 제형, 섭취 편의성, 하루 비용이며, 함량이나 가격이 높다는 이유만으로 더 좋은 제품이라고 판단하지 않는다.

질환 치료 중이거나 의약품을 복용하는 등 전문가 확인이 필요한 경우에는 개인화 추천을 제한하고 제품 정보와 상담 안내를 제공한다. 중복·병용 섭취에 관한 공식 주의정보도 반영한다. [식약처 중복·병용 섭취 안내](https://www.mfds.go.kr/brd/m_768/view.do?seq=3677)

## 4. 사용자 이용 흐름

### 설문형

서비스 소개·동의 → 관심 분야와 식습관 입력 → 건강 관련 주의조건 확인 → 기존 영양제 선택 → 추천 결과 → 근거 확인 → 제품 비교

### 대화형

서비스 소개·동의 → 사용자의 질문 입력 → AI의 추가 질문 → 조건 정리 → 제품·근거 검색 → 추천 결과 → 후속 질문과 비교

두 방식은 같은 제품 DB와 추천·주의 규칙을 사용한다. 설문 결과에서 대화를 이어갈 수 있도록 현재 세션의 입력 조건을 공유한다.

입력 항목은 다음과 같이 구성한다.

- 성인 여부
- 관심 건강 분야
- 식습관
- 예산과 선호 제형
- 현재 섭취 중인 영양제 및 확인 가능한 섭취량
- 알레르기, 의약품 복용·치료 여부 등 추천 제한에 필요한 선택 항목

건강 관련 질문에는 ‘모름’을 제공하고, 답변이 불충분하면 추천의 한계를 표시한다. 기존 제품을 확인할 수 없으면 성분 중복 검사가 완료된 것처럼 표시하지 않는다.

## 5. 필수 기능과 확인 기준

아래 기능을 Must 범위로 제안한다. 구현 여부는 개발 진행에 따라 별도로 기록한다.

| ID | 기능 | 확인 방법 | 기대 결과 |
|---|---|---|---|
| M01 | 이용 안내·동의 | 첫 방문 후 동의 전후 흐름 확인 | AI 생성 표시와 정보 처리 안내를 확인하고 진행 가능 |
| M02 | 설문 입력 | 관심 분야·식습관·기존 제품 입력 | 입력 검증과 조건 요약 제공 |
| M03 | AI 대화 추천 | 목적을 입력한 뒤 추가 질문에 응답 | 필요한 조건을 보완하고 제품·근거 검색 후 결과 제공 |
| M04 | 조건 기반 추천 | 검증용 설문 제출 | 조건에 맞는 후보 최대 3개와 추천 이유·출처 제공 |
| M05 | 제품 상세 | 추천 카드에서 상세 열기 | 가격·성분·함량·표시 섭취방법·주의사항·확인일 제공 |
| M06 | 성분 중복 확인 | 성분이 겹치는 검증용 제품 선택 | 중복 성분 표시 및 정보 부족 여부 안내 |
| M07 | 제품 비교 | 제품 2~3개 선택 | 같은 기준의 성분·함량·하루 비용 비교 |
| M08 | 대안 제품 추천 | 추천 제품의 대안 보기 선택 | 공식 자료가 있는 대안과 차이점 제공, 없으면 사유 안내 |
| M09 | 주의조건·근거 부족 처리 | 주의조건 또는 근거 없는 질문 입력 | 개인화 추천 제한 또는 확인 불가 안내 |

**M03·M04는 AI Agent와 RAG를 함께 사용하는 핵심 Must 기능**으로 구현한다.

첫 배포에서는 회원가입, 장기 기억, 사진 분석, 실시간 매장 재고 연동을 제외한다. 기본 추천과 비교가 안정적으로 동작한 뒤 확장 여부를 결정한다.

## 6. AI 설계 — Agent + RAG

### RAG: 확인된 자료를 검색해 답변에 활용

제품 정보, 제조사 자료, 공식 기능성·주의정보를 검색 가능한 지식 DB로 구성한다.

추천 요청과 사실 확인이 필요한 후속 질문마다 관련 자료를 검색하고, 검색 결과를 AI 입력에 포함한다. 답변에는 실제 사용한 출처를 연결한다.

가격·함량·섭취량 등 숫자는 구조화된 제품 DB에서 가져오고, 기능성·주의사항 설명은 검색 자료로 보완한다. 고정 문서를 항상 붙이는 방식으로 대체하지 않는다.

### AI Agent: 질문에 따라 필요한 도구 선택

| 도구 | 역할 |
|---|---|
| `search_products` | 조건에 맞는 검수 완료 제품 검색 |
| `search_evidence` | 성분·기능성·주의사항 근거 검색 |
| `check_overlap` | 등록된 제품 간 성분 중복 확인 |
| `compare_products` | 제품별 함량·제형·비용 비교 |

AI가 사용자 의도에 따라 2개 이상의 도구 중 필요한 호출 대상을 선택하고, 도구 결과를 확인한 뒤 답변한다.

예를 들어 기존 영양제를 입력한 사용자의 질문에는 제품 검색과 중복 확인을, 제품 차이를 묻는 질문에는 제품 비교와 근거 검색을 선택하도록 한다.

단, 추천 제한 조건과 데이터 검증은 서버가 강제 적용한다. AI가 주의 규칙을 생략하거나 검수되지 않은 제품을 추천할 수 없도록 한다.

### 출력 검증

- 추천 제품 ID가 실제 DB에 존재하는지 검사한다.
- 가격·성분·함량이 DB 값과 일치하는지 검사한다.
- 출처가 답변의 주장과 연결되는지 확인한다.
- 근거가 없거나 자료가 충돌하면 추천을 보류한다.
- 도구 호출 횟수와 응답 시간을 제한한다.
- 평가 증빙으로 도구명·검색 문서 ID·처리 결과를 기록하되 민감한 입력 원문은 남기지 않는다.

## 7. 상품 데이터 확보 계획

현재 실제 상품 목록은 미확정이다. **다이소 판매 사실과 정확한 표시사항을 확인한 제품만 추천 DB에 등록**한다.

수집 출처는 다음과 같이 구분한다.

| 출처 | 수집 목적 |
|---|---|
| 다이소몰 공식 상품 페이지 | 판매 상품명·상품번호·가격·규격·상품 링크 |
| 제조사·브랜드 공식 자료 | 정확한 성분·함량·섭취방법·주의사항 |
| 식품안전나라·식약처 | 제품·원료 정보와 공식 주의정보 확인 |
| 대안 제품의 공식 판매·제조사 페이지 | 비교 대상 제품의 사양·가격 확인 |

다이소몰에서 제조사 자료까지 확보되지 않으면 제조사 공식 사이트를 추가 확인한다.

### 초기 수집 목표 — 제안

다이소 제품 15~20종, 비교용 대안 제품 5~10종을 목표로 한다. 실제 확보 가능한 제품과 검수 시간을 확인한 뒤 범위를 확정한다.

### 필수 데이터

제품 ID, 상품명, 브랜드·제조사, 식품 유형, 가격, 포장 수량, 표시 섭취량·방법, 1일 섭취량당 성분·함량·단위, 기능성, 주의사항, 알레르기 정보, 출처 URL, 확인일, 검수 상태를 저장한다.

성분의 1정당 함량과 1일 섭취량당 함량을 구분한다. 단위나 성분 형태가 달라 직접 비교할 수 없으면 ‘단순 비교 불가’로 표시한다.

하루 비용은 포장 수량과 표시 섭취량을 모두 확인할 수 있을 때만 계산한다.

### 수집·검수 절차

1. 공식 상품 URL과 제품 식별정보를 확보한다.
2. 공개 자료에서 필요한 항목을 추출한다.
3. 자동 추출 결과를 원문과 대조한다.
4. 다른 팀원이 가격·함량·단위·섭취방법을 재검수한다.
5. 검수 완료 데이터만 서비스에 공개한다.

자동 수집은 접근 정책과 허용 범위를 확인한 뒤 적용한다. 상품 페이지 접근이 어렵다면 공개 공식 자료의 수동 검수·CSV 등록 방식으로 초기 DB를 확보한다.

수집된 사실 정보와 출처를 중심으로 사용하며, 상세페이지 이미지 전체를 그대로 재게시하는 방식은 피한다.

## 8. 시스템 구성과 기술 선택

서비스 요청은 다음 순서로 처리한다.

사용자 웹 화면 → 서버 입력 검증·주의조건 확인 → Agent의 도구 선택 → 제품 DB·근거 검색 → 응답 검증 → 결과 표시

| 영역 | 제안 기술 | 선정 이유 |
|---|---|---|
| 웹 화면 | Next.js·TypeScript | 설문·채팅·비교 화면을 하나의 웹 서비스로 구성 |
| 서버 | Python·FastAPI | 입력 검증, AI 처리, 데이터 가공을 Python으로 통합 |
| 데이터 저장 | PostgreSQL | 제품·성분·출처 관계와 숫자 정보 관리 |
| 근거 검색 | pgvector + 키워드·조건 검색 | 의미 기반 검색과 정확한 상품·성분 검색 병행 |
| AI | 도구 호출·구조화 출력을 지원하는 LLM | Agent 도구 선택과 검증 가능한 응답 구현 |
| 버전 관리 | GitHub | 코드·문서·이슈·PR·기여 이력 관리 |

기술은 팀의 숙련도를 확인한 후 확정한다. 관련 구현 기반은 [Next.js](https://nextjs.org/docs), [FastAPI](https://fastapi.tiangolo.com/), [PostgreSQL 벡터 검색 구성](https://supabase.com/docs/guides/ai/vector-columns) 공식 문서를 따른다.

배포는 웹·서버·DB를 외부 접근 가능한 환경에 구성한다. 서버 배포 후보로는 [Render의 FastAPI 배포 방식](https://render.com/docs/deploy-fastapi)을 검토한다. 실제 운영 요금과 제한은 배포 전 확인한다.

| 항목 | 계획 |
|---|---|
| 정확성 | 공개 제품의 숫자·섭취정보 전수 검수, 추천마다 출처 제공 |
| 개인정보 | 건강 관련 입력 최소화, 일반 이용·건강정보 처리 동의 구분 |
| 보관 | 초기 버전은 건강정보를 영구 저장하지 않고 세션 처리 후 삭제 |
| 외부 AI 전송 | 전송 항목·처리 목적을 안내하고 불필요한 식별정보 제외 |
| 보안 | API 키는 서버 환경변수에 보관, 사용자 화면·저장소에 노출 금지 |
| 장애 대응 | AI 호출 실패 시 오류·재시도 안내, 기존 제품 정보는 열람 가능 |
| 사용성 | 모바일에서도 설문·근거 확인·비교 가능 |
| 비용 | 세션별 요청·도구 호출·토큰 한도와 전체 예산 알림 설정 |
| 운영 유지 | 제출 후 결과 안내를 받을 때까지 접속 환경 유지 |

세션 데이터의 구체적인 삭제 시점과 외부 AI 제공자의 처리 조건은 공개 전 확정하고 안내문에 반영한다. 건강정보를 포함한 요청 본문이 오류 로그에 저장되지 않도록 한다.

실제 이름과 역량에 따라 조정한다. 각 담당 산출물은 다른 팀원이 검토하고, 모든 팀원이 본인이 작성한 기여 요약과 대표 커밋·PR·문서 링크를 README에 남긴다.

## 11. 개발 일정 — 4주 제안

| 기간 | 주요 작업 | 완료 기준 |
|---|---|---|
| 1주차 | 요구사항·화면·DB 설계, 상품 수집 가능성 검증, 기본 배포 | 검수 제품 5종으로 검색·상세 조회 가능, 외부 접속 성공 |
| 2주차 | 데이터 확대, 설문·RAG·Agent·추천 결과 연동 | 설문과 대화 모두 실제 DB·검색 근거로 추천 |
| 3주차 | 비교·대안·중복 확인·주의조건 처리, 통합 검증 | Must 기능 구현, 기능별 3회 실행 기록 확보 |
| 4주차 | 타깃 사용자 테스트, 개선·재검증, 문서·PDF 마무리 | 유효 사용자 5명 이상, 개선 증빙, 제출물 완성 |

1주차 초반에 데이터 확보 가능성을 먼저 확인한다. 자동 수집이 어렵다면 수동 검수 DB로 전환해 추천 기능 개발이 지연되지 않도록 한다.

개발 마감일, 주당 투입 시간, 총예산은 팀에서 추가 확정한다.

## 12. 사용자 검증과 과제 제출

팀원 지인 중 실제 타깃에 해당하는 일반 성인을 모집한다. 유효 참여자 최소 5명을 확보하되, 중도 이탈을 고려해 7~8명 모집을 제안한다. 팀원은 제외한다.

참여자는 다음 과업을 수행한다.

1. 설문으로 구매 후보를 찾는다.
2. 추천 이유와 주의사항을 확인한다.
3. 두 제품의 성분·하루 비용을 비교한다.
4. AI에 후속 질문을 한다.
5. 대안 제품과의 차이를 확인한다.

과업 완료 여부, 막힌 지점, 설명 이해도, 추천 근거에 대한 신뢰도와 개선 의견을 수집한다. ‘제품을 고르기 쉬워졌는가’를 평가하며, 건강 개선 효과를 검증한 것으로 해석하지 않는다.

피드백은 T1·T2 등 가명으로 기록한다. 공개 응답 원본에서는 이름·연락처와 식별 가능한 건강정보를 가린다. 각 의견에는 반영 내용과 커밋·전후 화면, 또는 반영하지 않은 이유를 연결한다.
